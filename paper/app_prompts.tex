\section{Agent prompts and task documents}
\label{app:prompts}

This appendix reproduces the documents the agents of Section~\ref{sec:agents}
received. They are the exact files, kept as they were. The only change is for
typesetting. A few symbols outside plain ASCII, such as Greek letters, arrows
and dashes, are written out in plain text. All three methods read the same task
documents. Open-ended research used no other prompt. Reflection and planning
added the prompts quoted after the task documents. Words in curly braces, or
words that begin with a dollar sign, are fields that the code filled in at run
time. The code that ran the sessions, relayed the model calls, and sent CFD jobs
to the compute machines is not included, because it only works on those
machines.

\subsection{The task document}
\label{app:prompts:task}

Every agent workspace held this file at \texttt{source/TASK.md}, and the
first message of an episode told the agent to read it. It states the objective,
the budgets, how a wing is handed over for evaluation, what the workspace
contains, and rules for fitting local models.

\begin{lstlisting}[style=prompt]
# Wing design task

Find a wing geometry with the best geometric mean of lift-to-drag across three
transonic conditions, trimmed to a fixed target lift coefficient.

| | |
|---|---|
| design vector | 38 physical parameters, `source/PARAMETERIZATION.md` |
| target lift coefficient | see `source/task.json` |
| Mach conditions | see `source/task.json` |
| objective | geometric mean of L/D over the three conditions |
| score eligibility | only a profile where all three conditions converge and trim |
| nominal evaluation horizon | 32 expensive evaluations |
| official surrogate budget | 4096 evaluations |

## How an evaluation happens

You do not run the expensive evaluation yourself and there is no way to launch,
poll or retry one from here. When you are ready, you hand over exactly one wing
with `python3 source/campaign.py hand-off` and finish your turn. The campaign
manager takes it from there and returns the result and every file it produced to
`observations/` before resuming you.

An evaluation can come back complete, or incomplete with no aggregate score. An
incomplete profile is a real outcome and is not a mistake on your part.

Two different things can be recorded:

* the **wing you hand over** is the next experiment;
* the **wing you nominate** (`campaign.py nominate`) is your current best
  recommendation.

They do not have to be the same wing.

## What is in here

| path | what it is |
|---|---|
| `source/superwing_public_dataset_v1.csv` | the SuperWing wing table, one row per wing, including the runs that failed |
| `source/running_info.jsonl` | the original run records: every flight condition tried on every wing, with its operating conditions, state and recorded outputs |
| `source/conditions.jsonl` | the same records as one row per (wing, condition), every field copied |
| `source/conditions.csv` | those rows flattened to scalar fields |
| `source/CONDITIONS_README.md` | field mapping, units, what each state means, and how absent slots are represented |
| `source/load_conditions.py` | a loader example that prints one converged condition, one failed condition and one absent slot |
| `source/PARAMETERIZATION.md` | what each of the 38 parameters means |
| `source/normalization.json` | population mean and standard deviation per parameter |
| `source/schema.json` | the fields an evaluation returns |
| `source/render_wing.py` | builds and draws a wing from a 38-D vector |
| `source/geometry.py` | optional normalization conversions and a dataset loader |
| `source/campaign.py` | task, budget, validation, official surrogate, handoff, nomination |
| `work/` | yours: code, models, candidates, plots, notes |
| `observations/` | evaluation results and their files, written for you |

`work/` is writable. `source/` and `observations/` are not.

## Analysis validity

Local models are useful search tools, but their diagnostics are not returned
evaluation results. When fitting or validating one:

* keep every condition row from the same `running_id` in the same train or
  validation split; a row split leaks the same wing across both sets;
* set and record random seeds before constructing the split or model, and save
  enough information to reproduce the split;
* evaluate the quantity used to choose a wing. Label condition-level or
  standardized errors as proxy diagnostics rather than held-out-wing objective
  performance;
* do not let a sentinel value or empty-filter fallback silently rank candidates
  that violate a stated feasibility or trim threshold. Either revise the rule
  explicitly or use a documented fallback;
* retain the local predictions for shortlisted candidates, and keep them
  distinct from official-surrogate results and returned expensive evaluations.

For a long surrogate batch, inspect status once if needed. To wait, use
`campaign.py surrogate-wait`; after it reaches a terminal state, use
`campaign.py surrogate-fetch`. Do not repeatedly poll `surrogate-status`.

## Domain

A geometry is admissible when every parameter lies inside the unit box after the
normalization in `source/normalization.json`. `campaign.py validate` tells you,
and nothing is silently clipped.
\end{lstlisting}

\subsection{The parameterization guide}
\label{app:prompts:parameterization}

Every workspace held this file at \texttt{source/PARAMETERIZATION.md}. It
explains what each of the 38 design variables means and how the section shapes
are built from them. It is the copy the agents read, kept as it was. Most of the
symbols written out in plain text for this appendix are in its formulas.

\begin{lstlisting}[style=prompt]
# SuperWing 38-D design-vector schema

This is the layout of the 38-dimensional wing geometry vector used by the
SuperWing dataset and by every 3D-wing surrogate. It is **dataset
documentation** -- the same parameterization spec the original researcher had at
v1, without which the dataset cannot be used. It describes what each dimension
*means*; it does not prescribe any defense.

A scalar 3D-wing surrogate's input is this 38-D vector with the two flight
conditions appended: `[geom(38), Mach, AoA]` -> 40-D.

## Layout

| Index / slice | Meaning | Notes |
|---|---|---|
| `0`       | Leading-edge sweep angle (degrees) | used in transonic Mach corrections (`M_eff = M*cos Lambda`) |
| `3`       | Aspect ratio (AR) | |
| `4`       | Taper ratio | tip chord / root chord |
| `7, 8, 9` | Section thickness ratios at 3 spanwise stations (root / mid / tip) | spanwise interpolation grid eta = `[0.0, 0.5, 1.0]` |
| `13, 14, 15, 16` | Twist (degrees) at 4 spanwise stations | spanwise interpolation grid eta = `[0.0, 1/3, 2/3, 1.0]` |
| `17 ... 26` | Upper-surface CST (Kulfan) weights `Wu` (10 coefficients) | |
| `27 ... 36` | Lower-surface CST (Kulfan) weights `Wl` (10 coefficients) | |
| `37`      | Root thickness factor (`tc_root`) | per-station thickness ~= `tc_root * rtcs[station]` |

Indices `1, 2, 5, 6, 10, 11, 12` carry additional planform / shape parameters of
the SuperWing parameterization and are not individually broken out here.

## CST sections

The upper/lower surfaces use a standard class-shape (Kulfan/CST) representation
of order 9 (10 Bernstein coefficients each). At a spanwise station with thickness
ratio `r` (interpolated from indices 7/8/9 on the eta = `[0, 0.5, 1]` grid), the
local section coefficients are `Wu*r` and `Wl*r`. Thickness at chordwise
fraction `x in [0, 1]` follows the usual CST form
`y(x) = sqrt(x) * (1-x) * sum_i W_i * C(9,i) * x^i * (1-x)^(9-i)`.

## 2D-section reconstruction

To query a 2D-section surrogate from a 3D wing, sections are reconstructed at
chosen spanwise stations eta: the local thickness-scaled CST coefficients (20
values) are concatenated with 8 context features
`[AoA_local, log10(Re), M_eff, eta, sweep, AR, taper, M_global]`, where
`AoA_local = AoA + twist(eta)` and `M_eff = M*cos(sweep)`. `Re` is taken at
`5x10^6`. This 28-D vector is the 2D-section surrogate's input; the reconstruction
is performed for you by `ctx.query.sections(...)`.
\end{lstlisting}

\subsection{The run-record guide}
\label{app:prompts:conditions-readme}

Every workspace held this file at \texttt{source/CONDITIONS\_README.md}. It
explains the SuperWing run records in the workspace, the field names, the units,
and what each solver state means. Its last section says the complete run
records were not public and could not be published without the SuperWing
authors' permission. That was true when the agents ran. The authors have since
given that permission, and the records are part of the released data.

\begin{lstlisting}[style=prompt]
# Flight-condition records

Each wing in this dataset was tested at up to eight flight conditions. The
compact wing table has one row per wing and does **not** carry the operating
conditions. These files do.

## Files

| file | what it is |
|---|---|
| `running_info.jsonl` | the original run records, one JSON object per wing, exactly as received from the dataset authors. Nothing has been altered. |
| `conditions.jsonl` | one row per (wing, condition slot), every field copied from the original record. Includes the 38-D geometry and the raw `working_conditions` block. |
| `conditions.csv` | the same rows as a flat table, for the scalar fields only. Use the JSONL if you want the full `results` block or the geometry. |
| `superwing_public_dataset_v1.csv` | the compact one-row-per-wing table. |

`conditions.jsonl` and `conditions.csv` are derived from `running_info.jsonl` by
copying. No value was imputed, rounded, rescaled or filled in. If a field is
null here, the original record has no value there.

## Field mapping, from the original record

| this view | original path |
|---|---|
| `running_id` | `running_id` |
| `geometry_38d` | `shape` |
| `state` | `{k}_state` |
| `mach` | `{k}_running_info.working_conditions.M3` |
| `aoa_deg` | `{k}_running_info.working_conditions.AA` |
| `reynolds` | `{k}_running_info.working_conditions.re` |
| `temperature` | `{k}_running_info.working_conditions.temp` |
| `results` | `{k}_running_info.results` (includes `wing_cl`, `wing_cd`, `err_cl`, `n_step` and further diagnostics) |
| `raw_working_conditions` | the whole `working_conditions` block, unedited |
| `source_pointer` | where in the original record the row came from |

Units: `mach` dimensionless, `aoa_deg` degrees, `temperature` as recorded in the
source, `reynolds` as recorded in the source. The source does not state units for
the last two beyond the field names; they are passed through unchanged rather
than converted.

## Condition states, and what has values

| state | count | operating values present |
|---|---|---|
| `Success` | 28,856 | yes |
| `CL fluctuation too large` | 4,563 | yes |
| `Simulation Diverge` | 2,788 | yes |
| `Not Simulated` | 137 | **no** -- nothing was run, so nothing was recorded |

A failed condition is a real record: it has Mach, angle of attack and a state,
and it tells you the solver was asked and did not give a usable answer. Failed
and not-run are different things and are not merged here.

## Two counts that are not the same number

* **36,352** possible slots: 4,544 wings times 8 condition indices.
* **36,344** recorded condition states.

The difference is eight slots on wing `1418` that are **absent from the record
entirely**. They are not eight failed solves. In `conditions.jsonl` and
`conditions.csv` those eight rows appear with `slot_recorded` false and every
other field null. Every other row has `slot_recorded` true.

## Provenance and publication

`running_info.jsonl` was supplied directly by the SuperWing authors and is **not
part of the public HuggingFace release**, which contains only converged results.
Internal use in this project is authorized. Publishing anything derived from this
file needs the authors' permission first. That question is separate from, and
unaffected by, any internal use here.

`load_conditions.py` in this directory prints one successful condition, one
failed condition and one absent slot, so you can see how each is represented.
\end{lstlisting}

\subsection{The reflection prompt}
\label{app:prompts:reflect}

The reflection method ran this prompt in a fresh session after every
returned CFD result. That session read the result and the trace of the turn
that produced the wing, then wrote a reflection file and updated a running list
of lessons. The next turn of the main session received the new reflection and a
summary of the lesson list, capped at 4,000 characters. Earlier reflections
stayed readable.

\begin{lstlisting}[style=prompt]
You are the self-reflection stage of a research agent that works on a wing-design task in the persistent workspace $episode_root. An expensive evaluation of one of the agent's wings has just returned. Your job is to reflect on that attempt and record lessons the agent will use in its next decisions. You do not design or hand over wings. You do not change the evaluation: its result is the pinned evaluator's measurement.

WHAT RETURNED: evaluation $rid. Result file: observations/$rid.json. Files it produced: observations/${rid}_artifacts/.
$outcome_text

THE ATTEMPT: $trace_file records the research turn that produced this wing: the message the agent received, the agent's messages, its tool calls with shortened outputs, and the handoff. $trace_note

EXISTING LESSONS: $lessons_state

Read the evaluation files and diagnostics before you write. Then write two files:

1. $reflection_file: a concise reflection with these sections.
   - Attempt: what the agent tried and why, citing the trace.
   - Result: what returned, as facts, citing the observation file and diagnostics.
   - Lessons: what this result teaches, each lesson linked to its evidence. If the result was useful, include what went well.
   - Uncertainties: what this single result cannot establish.
   - Next: concrete improvements to try in upcoming decisions.
2. work/reflexion/LESSONS.md: the cumulative lesson list. Keep every earlier lesson, and mark any that this result contradicts rather than deleting it. Add the new lessons, tagged with $qtag. Keep a short "Current summary" section at the top.

Write only these two files. Then finish your turn with a one-line confirmation.
\end{lstlisting}

\subsection{Planning step 1, the learner prompt}
\label{app:prompts:learner}

The planning method ran a cycle of stages before each hand-off. Step 1,
the learner, writes a memo of what the results so far show. Step 2 runs four
planners, and each writes one plan of two steps. Step 3, the evaluator,
predicts the delivery and $L/D$ of each planned step. Step 4 has no prompt. A
fixed formula keeps the plan with the best expected $L/D$. Step 5, the
executor, is the main session carrying out the first step of the selected plan.
The agent could plan again at most three times per decision. The learner,
planner and evaluator had to answer with one JSON object that matches a schema,
and a correction message was sent when a reply did not. This is the learner
prompt.

\begin{lstlisting}[style=prompt]

---
$campaign_message
---

PLANNING CYCLE: decision $decision_id, cycle $cycle. The frozen planning root for this cycle is $root_file.
$previous_memo_line
$cycle_context

\label{app:prompts:executor}

This message went to the main session of the planning agent. It begins
with the manager's turn message. The session ran the first step of
the selected plan, handed over one wing, and wrote a report.

\begin{lstlisting}[style=prompt]
$campaign_message

Your planning stages selected $selected_label by the fixed comparison rule (records: $cycle_dir/selection.json).

$procedure
