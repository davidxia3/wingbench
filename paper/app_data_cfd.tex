\subsection{Recommendations and wings}

Table~\ref{tab:data-recommendations} describes \texttt{recommendations.csv}.
The file \texttt{wings.csv} has the column \texttt{wing} and the 38 design
variables \texttt{x00} to \texttt{x37}, in physical units
(Table~\ref{tab:data-wings}). It covers the 3,294 wings of the four
surrogate-assisted baselines, the 741 SMAC3 wings, and the 1,165 agent wings

against its fingerprint. Five agent wings whose requests stopped before a
document was written appear in the other tables by their hash only. 43 of
the agent wings lie on the edge of the design box, up to $9\times10^{-16}$
standardized units outside it once their physical values are standardized
again. The campaign accepted and graded them, and the released episode
machine accepts a proposal within $10^{-9}$ standardized units of the edge,

\subsection{SuperWing records}

SuperWing is the wing dataset the benchmark is built on. Its complete run
records are redistributed in \texttt{data/superwing/} with the SuperWing
authors' permission. \texttt{superwing\_records.csv} has one row per wing
for all 4,544 wings, with the same 38 variables as \texttt{wings.csv},
whether the mesh step worked, and the result of each of the wing's 8 flight
conditions. It was built from the complete run record,
\texttt{running\_info.jsonl}, while the public release of SuperWing contains
only the converged results. \texttt{cruise\_ld\_percentiles.json} holds the
dataset's cruise-band lift-to-drag percentiles. Of the 36,344 tests, 28,856
succeeded. 4,563 failed because the lift kept changing and never settled,
2,788 failed because the simulation blew up, and 137 were never run. The
often-used table of 4,239 wings lists only the wings where at least one of
the 8 tests succeeded, so it leaves out the 305 wings that failed every
test. The column \texttt{any\_success} is 0 for those 305.

\subsection{Further notes from the data card}

The SMAC3 records name the reason for each nondelivery but not the outcome
type, so SMAC3's \texttt{outcome} column is empty, and 18 nondeliveries its
run controller recorded without a reason carry \texttt{undetermined}. Three
SMAC3 evaluations have no wing hash, because their evidence was lost. The
agent export left out the scores of the 90 private grades made before the
first query and the reason codes of all 136 agent private grades. Both were
filled in from the grader's result documents, the reason codes by the rule
the export used for the other rows, checked against every evaluation that
has both a code and a document. The 39 agent requests that stopped before a
document was written keep their recorded outcome and no score. SMAC3's
\texttt{cfd\_core\_seconds} and \texttt{timed\_evaluations} include two
checkpoint-32 grades that were replaced when two SMAC3 episodes were run
again, and the paper's cost numbers use these totals. The 44 GB of raw CFD
output, the optimizers' full logs, and the agents' full execution traces are
not included.

\section{CFD protocol and environment}
\label{app:cfdprotocol}

{\sloppy
The grading protocol is the file
\texttt{configs/cfd/final\_protocol\_candidate\_v2.json}. The configs README
describes it as the grading protocol the benchmark ran with, and it pins the
grader's source files under \texttt{scripts/cfd/} by content. The grader
\texttt{grade\_benchmark.py} builds the mesh of one wing, runs the three
flow conditions in series at fixed lift, and writes the result document.
\texttt{grading\_protocol.py} loads the protocol and refuses to run if any
pinned file has changed, and \texttt{task\_protocols.py} derives the
low-load and high-load protocols from this file, changing only the lift
target and its angle-of-attack seed. The values below are copied from the
protocol file, and a field quoted in typewriter type without a plain reading
is reproduced as written. The file's own identity fields are
\texttt{protocol\_id} \texttt{superwing-fixed-cl-v5-candidate-c},
\texttt{protocol\_revision} \texttt{3}, \texttt{protocol\_status}
\texttt{qualification\_required}, \texttt{official\_grading\_enabled}
\texttt{false} and \texttt{benchmark\_release\_id} \texttt{null}. Its scope
block names the geometry schema \texttt{superwing-38d-v1}, one mesh per
wing, conditions run one after another, and
\texttt{partial\_scores\_official} \texttt{false}. The
\texttt{geometry\_hash\_algorithm} is
\texttt{sha256(superwing-geom38-f64le-v1-NUL + 38xf64le)}, which reads as
the SHA-256 of a fixed prefix string, a NUL byte and the 38 coordinates as
little-endian 64-bit floats, and it is the \texttt{wing} identifier of the
released tables.
\par}

\subsection{Flow conditions and trim procedure}

Every task uses the same three conditions and flow reference quantities.
The protocol file carries the nominal task, and the other two tasks change
only the target lift coefficient of the three conditions and the
angle-of-attack seed (Table~\ref{tab:cfd-tasks}). Each seed is the exact
median, with no rounding, of the recorded angle of attack over the
successful SuperWing cases whose lift coefficient lies within 0.02 of the
target, over all recorded Mach numbers. The nominal seed comes from
\texttt{configs/cfd/seed\_aoa\_selection\_v1.json}, whose band 0.39 to 0.43
held 1,198 cases, and the low and high seeds from
\texttt{seed\_aoa\_selection\_load\_low\_v1.json}, band 0.13 to 0.17 with
994 cases, and \texttt{seed\_aoa\_selection\_load\_high\_v1.json}, band 0.64
to 0.68 with 1,172 cases. All three files state that the seed applies to
every wing and condition and that no reselection is allowed. Both load
files carry a freeze time of 2026-08-02. The protocol's seed policy is
\texttt{fixed\_per\_condition} with \texttt{selection\_rule}
\texttt{exact\_median\_successful\_cases\_in\_cl\_0.39\_0.43\_no\_rounding}.

Each condition is solved at fixed lift. The ADflow runner calls the solver's
lift-matching routine \texttt{solveCL} with the target lift, the seed angle
of attack and the options of the \texttt{solver.solvecl} block. The
release's patch to the runner makes every option explicit, so that a change
of a library default cannot change the protocol, and records the routine's
result in the output. The options with a plain reading are \texttt{delta}
\texttt{0.5}, the first step in angle of attack in degrees, \texttt{tol}
\texttt{0.001}, the lift tolerance the matching loop aims for before the
condition gate accepts a lift within 0.02 of the target, \texttt{max\_iter}
\texttt{20}, at most 20 matching iterations, \texttt{clalpha\_guess}
\texttt{null}, no starting guess of the lift slope, and
\texttt{write\_solution} \texttt{true}. The remaining options are
reproduced as written. They are \texttt{auto\_reset} \texttt{false},
\texttt{relax\_clalpha} \texttt{1.0}, \texttt{relax\_alpha} \texttt{1.0},
\texttt{l2\_convergence\_rel} \texttt{null}, \texttt{stop\_on\_stall}
\texttt{false}, \texttt{work\_unit\_time} \texttt{null} and
\texttt{update\_cutoff} \texttt{1e-16}.
\par}

\subsection{Mesh and solver settings}

The mesh recipe is the SuperWing dataset default, built once per wing by the
SuperWing mesh generator (Table~\ref{tab:cfd-mesh}). The flow solver is
ADflow on the RANS equations, run as 16 MPI ranks with one thread each
(Table~\ref{tab:cfd-solver}). The protocol requires six environment
variables in every ADflow process. The released grader refuses to start when
any variable that begins with \texttt{ADFLOW\_}, or any of the three thread
variables, is set in its own environment. It then adds the six values
itself, from the protocol, to the environment of every \texttt{mpirun}
child, and passes only a fixed list of other variables through. The
protocol has no iteration limit on a condition beyond \texttt{n\_cycles} and
\texttt{n\_cycles\_coarse}. Its limits per step are wall-clock time, 1800
seconds for meshing and 7200 seconds for each flow condition, with no
retries after an infrastructure failure. Those are the grading job's own
settings. Retrying a job after a machine failure was the campaign
controller's task, and the ten charged requests in
Appendix~\ref{app:agent-comparison} are the cases where that layer did not
retry.

\subsection{Condition gates, outcomes and aggregation}

A condition is valid only if every gate of Table~\ref{tab:cfd-gates} holds.
The protocol file itself has only the positivity gates on lift, drag and
lift-to-drag ratio. The upper limit of 40 on each lift-to-drag ratio is
part of the benchmark objective in the rules, and the released local grader
applies it as the $(0,40]$ envelope. The rules state the delivery condition
in one sentence. A CFD evaluation delivers a score only if all three
conditions return a valid result, the lift is within 0.02 of the target,
every lift-to-drag ratio is above 0 and at most 40, and the angle of attack
is between $-10$ and 25 degrees. Otherwise the evaluation returns a failure
type and no score. The failing gate is recorded as a reason code.

\subsection{Execution environment}

The recorded results come from AWS \texttt{m7a.4xlarge} machines with 16
vCPUs and 64 GB of memory. One wing was graded per machine at a time, and
each CFD job used all 16 cores as 16 MPI ranks with one thread each and had
the full 64 GB. The grader enforces one job per machine with the lock file
of Table~\ref{tab:cfd-solver}. The three conditions run one after another,
so one wing can take up to six and a half hours. A job that reaches a limit
is stopped and recorded as inconclusive. It gets no score, and the wing does
not count as delivered. On a slower machine, on a machine where two ranks
share one core, or with less memory so that the solver swaps, the same wing
takes longer and more wings reach the limits. The rules note that about one
third of the reference nondeliveries were set by a time limit, require an
\texttt{m7a.4xlarge} or a faster machine for comparisons with the reference
results, and state that a later version will replace the time limits with
iteration limits.

\subsection{What a rebuild reproduces}

The release rebuilds the container from the public base image with a
Dockerfile and an Apptainer definition in \texttt{benchmark/environment/}.
On 2026-09-25 the Docker image was built from that folder on a new
\texttt{m7a.4xlarge}, the four SuperWing files were fetched, and
\texttt{benchmark/grade\_local.py} graded one recorded wing. All three
conditions returned lift, drag, angle of attack and lift-to-drag ratio
identical to the recorded values, the score equaled the recorded
33.401823323619524, and the grade took 2 hours 13 minutes. The folder
\texttt{rebuilt\_test/} holds that result document, the grader's log, the
fetch log and the image digest of the rebuilt container. The environment
document lists four things the rebuild does not reproduce. First, the exact
image that graded the wings, since the rebuilt image has the same content
but a different digest. Second, the runtime fingerprint. The probe report
includes the host kernel version, the path of every module, the account ids
and the values of \texttt{PATH} and similar variables, so a rebuilt
environment produces a different report and the released grader stops with
a fingerprint mismatch. To grade with a rebuilt environment one must run the
probe, write its hash into a copy of the protocol, and treat that copy as a
new protocol revision. Results graded under it are the user's own and not
the recorded results, and the tested rebuild therefore carries
\texttt{grading\_mode} \texttt{local} in its result document. Third, the
grader's other inputs. \texttt{grade\_benchmark.py} also requires an
authorization file, a runtime attestation file and a publication journal,
and the tools that produced the first two ran on the recorded machines and
are not in the release. Fourth, the surrogate, which runs outside the
container.
